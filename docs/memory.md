# Memory System Reference

The optional SurrealDB memory store saves documents by scope and retrieves context for OpenAI-compatible chat requests. A dedicated local service can also use semantic embeddings.

---

## Building with Memory

```bash
cargo build --release --locked --features memory
```

The `memory` Cargo feature adds SurrealDB and the memory routes. The service must also set `memory.enabled` and successfully open the database. With the feature compiled in, memory routes return HTTP 503 if the store is unavailable.

---

## Configuration

In the [service configuration file](config.md):

```toml
[memory]
enabled = true
db_path = ""                          # defaults to memory.db under the platform's oproxy data directory
embedding_model = "text-embedding-3-small"
```

`db_path` supports tilde expansion: `~/.local/share/oproxy/memory.db`

Set `PROXY_EMBEDDINGS_API_KEY` in the dedicated local service's environment to enable separately billed OpenAI embeddings. With the variable unset, the service retrieves local documents without an embedding call. Shared deployments always use local document retrieval.

## Scope Concept

Every document belongs to a **scope** — a string namespace for isolation. Common scopes:

| Scope | Purpose |
|-------|---------|
| `session` | Ephemeral per-session context (default) |
| `project` | Shared across a codebase |
| `global` | User-wide persistent knowledge |

In dedicated local mode, set `X-Memory-Scope` on chat requests. The default is `session`. Document creation takes a `scope` in its JSON body. List and search accept `scope` as a query parameter and default to `session`. Delete uses the document ID. In shared mode, the proxy assigns a scope to each authenticated principal and enforces it for retrieval, creation, listing, search and deletion.

## REST API

### Store a Document

```
POST /v1/memory/documents
Content-Type: application/json

{
  "scope": "project",
  "text": "The auth module uses JWT with RS256 signing.",
  "metadata": { "source": "codebase-review" }
}
```

Response: `{ "id": "<uuid>" }`

When the dedicated service has an embeddings key, it uses `text-embedding-3-small` by default and stores the vector in a 1536-dimensional HNSW index. The embedding request has a 500 ms deadline. The document can be stored without a vector when embedding is unavailable.

### List Documents

```
GET /v1/memory/documents?scope=project
```

Response: array of `DocumentRecord` objects.

### Delete a Document

```
DELETE /v1/memory/documents/<id>
```

Response: `204 No Content`

### Semantic Search

```
GET /v1/memory/search?q=authentication&scope=project&limit=5
```

With embeddings, search returns the nearest documents ordered by cosine distance. If embeddings are unavailable, it returns up to `limit` documents from the selected scope with no distance score.

## RAG Injection Behavior

When a chat request arrives:

1. The proxy combines text from user messages.
2. It searches the selected scope for up to three documents with a 500 ms deadline.
3. If results are found, prepends a system message:

```
# Relevant Context

- The auth module uses JWT with RS256 signing.
- Token expiry is 24 hours for API keys, 1 hour for OAuth.
```

4. The enriched request is forwarded to the backend.

---

## Embedding Model Configuration

The default model is `text-embedding-3-small`. The HNSW index expects 1536 dimensions and the proxy requests the model's default output size. Use a compatible model. If you switch models, re-embed the documents in a fresh store so search compares vectors generated by the same model.
