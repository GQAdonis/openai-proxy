# Candidate acceptance scenarios

The operator supplied the product outcomes and both deployment modes. These examples, version targets and time budgets are proposed inputs to the VLBV contract. No scenario has been executed. Frequency is **UNKNOWN** for each candidate until operator calibration or telemetry is available. The observable in the third column should come from outside the component being assessed.

| Candidate and actor | Real entry and reason for inclusion | Observable and control |
|---|---|---|
| 1. Local owner completes an external login | Keep the proxy running. Exercise the actual CLI-to-store write shape in a temporary home. Cover replace-by-rename, a mount visible to the container, keyring-only change and a missed watcher event. This is the primary user operation. | Independent upstream sees identity B and the matching header/profile on the first eligible post-reconciliation request, same service PID. Proposed bounds are 2 s for file notifications and 30 s for keyring/poll recovery. Check a token change for the same account as well as A→B. Repeat in long-lived `serve` HTTP, ACP and MCP modes. Fresh `setup opencode` derives models from the same effective identity. A partial file or noisy unrelated home file cannot publish a mixed identity. An actual account login is a separate authorized demonstration. |
| 2. An expired managed login serves concurrent requests | Request a turn just before/after expiry, advance a fake clock, submit concurrent turns, exercise bounded 401 recovery and manual refresh. Rotation can invalidate an earlier refresh token. | Count credential-owner requests, upstream generations and turn/tool effects. One managed refresh per identity, store-confirmed new generation for new turns. API-key/external modes never call managed refresh. Revocation requests sign-in, 429 preserves quota state, and no output/tool request is replayed. |
| 3. Logout or account switch races refresh | Complete login B or logout while refresh A is delayed, then release A. Include startup without auth and a changed custom store. Rare, high-impact account confusion. | Independent backend never sees A after logout/new generation. Signed-out service remains recoverable by its owner. A stale request cannot silently switch accounts mid-turn. A parse/read failure cannot fall through to a different user's key or keyring. |
| 4. Subscriber uses the OpenCode V2 plugin | Load local and packed V2 plugin in the pinned host and select its provider. Preserve an existing provider override. Use a mocked Codex boundary and separately an owner-authorized Pro turn. | Host verifies provider/model discovery and a streamed turn with one executor. Real-account evidence identifies the intended allowance and outcome without logging credentials. Fixture or provider label alone cannot prove allowance. Quota denial or an unknown plan cannot switch to API billing. |
| 5. Admin configures OpenCode on this machine | In a disposable config home with a preexisting user provider, comments and competing config layers, preview/apply twice, inspect from a different directory and undo. | Actual host resolves intended provider/path/model at project and global scope. Unrelated entries/comments survive, second apply is a no-op, undo removes only owned entries. Concurrent, invalid or unwritable inputs produce an actionable error without truncation. A project-local discovery cannot pass the global case. |
| 6. Chat user selects each SDK driver | On the same REST chat application create and resume a conversation per driver. Stream a tool-bearing turn and cancel another. Direct REST clients still exercise their existing entry. | Observe driver invocation, native session ID, incrementally rendered answer, terminal outcome and exactly one tool effect. Cancel reaches native runtime. Input from another user, mismatched workspace or forged permission reply cannot resume or act on a session. A stopped browser animation alone does not prove interruption. |
| 7. Operator deploys embedded console locally and shared | Build clean binary and release image, launch from an empty working directory, open chat/settings, edit an asset and rebuild, exercise UI build failure. Test a shared chat user and admin directly via HTTP. | Browser gets correct assets, route/MIME/cache behavior, keyboard-accessible chat, continued partial output and authorized settings. Missing asset/API gets a genuine error. No frontend dev server is present. A chat user's direct admin request fails with no refresh or host write. Missing SDK runtime is distinguishable from missing web assets. |
| 8. Editor user connects over ACP | Provision Zed and a second compatible editor with the stdio launch manifest, initialize, start a session and send a prompt. | Editor observes streamed text and accurate terminal status. Protocol-only stdout, disabled unsupported capabilities and a real failure path differentiate ACP from MCP. A syntactically valid config never launched by the editor is insufficient. |
| 9. Tool user connects to this MCP server | Use a detected client's registration workflow and a temporary home, for stdio and for supported HTTP clients. List tools and invoke a benign one. | Client observes the expected tools and a version-compatible exchange; removal preserves other servers. A config-file search or `/health` alone cannot pass. A chat-only client cannot read another account's auth metadata or reach privileged setup. |
| 10. Chat user sees a validated A2UI surface | Through AG-UI deliver a typed create, component/data update and delete. Activate one approved control from the keyboard. Interleave plain text and a second user's surface with the same surface ID. | Browser accessibility tree and visible state reflect the correct update and one authorized action. JSON in plain text stays text. Malformed/oversized messages, unknown catalogs, foreign surface actions and unsupported versions leave the last safe state and text usable. |
| 11. Admin inspects service features | Cover the inventory in native/container, memory-enabled/disabled, HTTP/stdio and shared/local modes with overridden settings. Exercise a scoped document operation and hook delivery using synthetic data. | Compare effective UI status with independent CLI/process/client observations, including disabled/degraded features, A2A card visibility, tool source, model catalog, skills limit, hook emission and memory scope. An edited value masked by env or a startup-only change cannot display as active. |

**Calibration and exclusions.** Prioritize 1, 4, 6 and 10 as user-facing journeys. Keep the logout race, partial write, double tool execution and cross-user action as rare critical controls. Collect owner timing expectations, target editor/MCP versions, allowed workspace/tool policy and consent for live entitlement evidence during contract adoption. Arbitrary third-party clients, unvalidated remote component catalogs, household sharing of a subscriber login and automatic API billing fallback do not count as delivery evidence.
